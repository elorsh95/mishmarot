# משמרות – ניהול סידור עבודה שבועי

מערכת web לניהול סידור עבודה שבועי לנציגי מכירות במוקד טלפוני. ממשק בעברית מלאה (RTL), מותאם למובייל.

- **מנהלי צוותים** משבצים את הנציגים שלהם לפי שבוע: משמרת (בוקר / ערב / כפולה), מיקום עבודה, או היעדרות.
- **חוק החריגים:** מעבר למכסה החודשית (ברירת מחדל: 2 ימים בחודש קלנדרי) לעבודה ממיקום שדורש מכסה (למשל "בית"), כל שיבוץ נוסף ממתין לאישור.
- **מנהלת המוקד** מאשרת או דוחה (עם הערה) במסך "בקשות לאישור", צופה ועורכת את כל הצוותים.
- **מנהל המערכת** מנהל משתמשים, תפקידים והרשאות, צוותים והגדרות.
- נציגים אינם משתמשים במערכת.

## טכנולוגיה

| שכבה | בחירה |
|---|---|
| Framework | Next.js 16 (App Router) + TypeScript |
| DB | Cloud Firestore (דרך Firebase Admin SDK, בצד השרת בלבד) |
| התחברות | Firebase Authentication (שם משתמש + סיסמה, סיסמאות מנוהלות ומוצפנות ע״י Firebase), session cookie מסוג httpOnly |
| UI | Tailwind CSS v4, רכיבים משלנו ב-`src/components/ui`, אייקונים lucide |
| ולידציה | Zod |
| בדיקות | Vitest (יחידה) + Firebase Emulator (אינטגרציה) |
| אחסון | Firebase App Hosting |

## הרצה מקומית

דרישות: **Node.js 22**, **Java 21** (לאמולטור של Firebase).

```bash
npm install
cp .env.example .env.local     # מפנה את האפליקציה לאמולטור

# טרמינל 1: אמולטורים של Firestore ו-Auth (הנתונים נשמרים בין הרצות ב-.emulator-data)
npm run emulators

# טרמינל 2: נתוני דמו, ואז שרת הפיתוח
npm run seed                   # פעם אחת. להתחלה מחדש: npm run seed -- --reset
npm run dev
```

פותחים את http://localhost:3000. ממשק האמולטור (צפייה בנתונים) זמין ב-http://localhost:4000.

## מבנה הפרויקט

```
src/
  app/
    (auth)/login/          התחברות
    (app)/                 כל המסכים אחרי התחברות (layout עם תפריט לפי הרשאות)
      schedule/  approvals/  agents/  transfers/
      teams/  users/  roles/  settings/  audit/  account/
  components/
    ui/                    רכיבי UI משותפים (Button, Dialog, Field…)
    layout/                מעטפת האפליקציה ורשימת התפריט (nav-items.ts)
  lib/                     תשתית: firebase, תאריכים, שגיאות, runAction, events
  modules/                 הלוגיקה העסקית, מודול לכל תחום
    permissions/           קטלוג ההרשאות ובדיקות (can / canForTeam / teamScope)
    schedule/              engine.ts (כל שינוי בסידור), quota.ts (חוק המכסה), service.ts
    approvals/  agents/  transfers/  teams/  users/  roles/  catalog/  settings/  audit/  auth/
scripts/                   seed, bootstrap
firestore.rules            חסימת גישה ישירה מהדפדפן (כל הגישה דרך השרת)
firestore.indexes.json     אינדקסים מורכבים
```

**עקרונות:**
- **שכבת ה-services היא מקור האמת.** כל service מקבל את המשתמש המבצע (`actor`) ובודק הרשאה בעצמו. דפים ו-actions הם שכבה דקה מעליו. דוחות, ייצוא וממשקי API עתידיים יקראו לאותם services.
- **הרשאות:** הקוד בודק מפתח הרשאה (למשל `schedule.edit`). איזה תפקיד מחזיק איזו הרשאה, ובאיזה היקף ("כל הצוותים" או "הצוותים שלו בלבד"), נשמר ב-DB וניתן לעריכה במסך "תפקידים והרשאות".
- **כל שינוי בסידור** עובר דרך `applyChanges` ב-`modules/schedule/engine.ts`, בטרנזקציה אחת: בדיקת הרשאה ונעילות, כתיבה, חישוב מחדש של חוק המכסה לכל נציג וחודש שהושפעו, פתיחה או ביטול של בקשות אישור, ורישום בלוג.
- **לוג פעולות** נכתב באותה טרנזקציה של השינוי (`auditInTx`).
- **אירועים** (`lib/events.ts`): למשל `approval.requested` או `week.published`. זו נקודת החיבור להתראות עתידיות, בלי לגעת בלוגיקה.

### חוק המכסה (עבודה מהבית)

- לכל מיקום עבודה יש סימון "דורש מכסה" (כברירת מחדל רק "בית").
- **תקופת המכסה** נקבעת בהגדרות: **שבועית** (ראשון עד שבת) או **חודשית** (חודש קלנדרי). ברירת המחדל היא חודשית.
- הספירה נעשית לכל נציג בנפרד בכל תקופה, לפי **סדר התאריכים** ולא לפי סדר ההזנה.
- המכסה של נציג היא המכסה האישית שלו, אם הוגדרה, ואחרת ברירת המחדל מההגדרות (2).
- ימים 1 עד N נספרים "במסגרת המכסה". מהיום ה-N+1 והלאה השיבוץ "ממתין לאישור" ונפתחת בקשה.
- יום שנדחה לא נספר, ונשאר בסידור מסומן באדום עד שמנהל הצוות משנה אותו. יום שאושר נשאר מאושר.
- אם מוחקים או משנים יום מוקדם יותר, בקשה שנכנסת בחזרה למכסה נסגרת אוטומטית. כל זה נרשם בלוג.
- שינוי מכסה של נציג, שינוי מכסת ברירת המחדל או מעבר בין שבועית לחודשית מחשבים מחדש את התקופה הנוכחית ואת התקופות הבאות. בקשות שכבר לא נדרשות נסגרות, ונפתחות בקשות לפי הכלל החדש. תקופות שעברו לא משתנות.

### נעילות ופרסום

- שבוע שעבר נעול לעריכה. רק מי שמחזיק בהרשאה `schedule.editLocked` (מנהל מערכת ומנהלת מוקד) יכול לערוך אותו.
- סידור שפורסם נעול למנהל הצוות עד שהוא מחזיר אותו ל"טיוטה". מנהלת המוקד יכולה לערוך גם סידור שפורסם.

### העברת נציג בין צוותים

מנהל הצוות המקבל שולח בקשה ממסך "העברות נציגים", ומנהל הצוות הנוכחי של הנציג מאשר. באישור, השיבוצים מהיום והלאה עוברים עם הנציג, וההיסטוריה נשארת בצוות הקודם. מנהל מערכת ומנהלת מוקד יכולים גם להעביר ישירות ממסך הנציגים.

### שיבוץ מהיר
- **היעדרות לטווח תאריכים:** בחלון השיבוץ בוחרים היעדרות וממלאים "עד תאריך". אותה היעדרות נרשמת בכל ימי הטווח, עד 62 ימים ואפשר גם על פני כמה שבועות. חגים ושבתות מדולגים. ברירת המחדל היא רק ימי העבודה הקבועים של הנציג, ואפשר לבטל את זה. שיבוצים קיימים בימים האלה מוחלפים.
- **שיבוץ מרוכז:** "בחירה מרובה" בסרגל הכלים. לוחצים על משבצות, על יום בכותרת (כל הנציגים באותו יום) או על שם נציג (כל השבוע שלו). אחר כך "שיבוץ לנבחרים" קובע משמרת ומיקום, היעדרות או הסרה לכולם יחד.
- **בשני המקרים** חלים אותם כללים כמו בשיבוץ רגיל: מכסת בית ובקשות אישור, חגים ושבועות נעולים. משבצות שלא ניתן לעדכן מדולגות ומוצגות ברשימה.

### שיתוף הסידור עם הנציגים
הנציגים לא משתמשי מערכת, ולכן אפשר לשתף איתם קישור לצפייה בלבד. בסידור השבועי: **"שיתוף עם הנציגים"** ← יצירת קישור ← העתקה או **שליחה בוואטסאפ**.
- הקישור קבוע לכל צוות. שולחים אותו פעם אחת לקבוצה, והוא תמיד מציג את הסידור העדכני.
- בדף מוצגים **רק שבועות שפורסמו**: שמות, משמרות, מיקומים, היעדרויות וחגים. הערות, מספרי עובד ופרטי אישורים לא מוצגים.
- הדף מותאם לטלפון, אפשר לעבור בו בין שבועות, ויש בו כפתור **"שמירה כתמונה"** לשליחה בוואטסאפ.
- **"החלפה בקישור חדש"** מבטלת מיד את הקישור הקודם, למשל אם נציג עזב. אפשר גם לבטל לגמרי.
- ניהול הקישור דורש הרשאת פרסום סידור לצוות. הקישור הוא מחרוזת אקראית של 256 ביט, והדף לא נסרק במנועי חיפוש. יצירה וביטול של קישור נרשמים ביומן הפעולות.

### חגים וערבי חג
חגי ישראל נקבעים אוטומטית לפי לוח השנה העברי (ספריית `@hebcal/core`, לוח ישראל).
- **חג** (ראש השנה, יום כיפור, סוכות, שמיני עצרת, פסח ראשון ושביעי, שבועות, יום העצמאות): המוקד סגור, ואי אפשר לשבץ ביום הזה.
- **ערב חג** (ערבי החגים, הושענא רבה, ערב שביעי של פסח, יום הזיכרון): משבצים כמו ביום שישי, כלומר רק במשמרות שמתקיימות בשישי (בוקר).
- **חול המועד, חנוכה, פורים ועוד:** השם מוצג בסידור, והיום עובד כרגיל.
- מסך **הגדרות** ← **חגים וימים מיוחדים** (למנהלת המוקד ולמנהל המערכת): אפשר לשנות כל יום, למשל לקבוע חול המועד כערב חג או יום העצמאות כיום רגיל, או להוסיף יום מיוחד כמו יום גיבוש. כל שינוי נרשם ביומן הפעולות, ואפשר להחזיר יום ללוח השנה.
- "מילוי לפי ברירת מחדל" ו"העתקה משבוע קודם" מדלגים על חגים, ועל משמרות שלא מתקיימות בערב חג, בלי להציג שגיאות.

### דוחות וייצוא ל-Excel
- **דוחות** (מסך **דוחות**): בוחרים תקופה: **יום** (כולל בחירת תאריך מסוים), **שבוע**, **חודש**, **3 חודשים** אחורה או **טווח תאריכים** חופשי (עד שנה). החצים עוברים לתקופה הקודמת או הבאה, ו"נוכחי" חוזר לתקופה של היום. אפשר לסנן לפי צוות.
  - **לפי נציגים:** לכל נציג מוצגים ימי העבודה (גם לפי משמרת), ימי הבית מול המכסה, הימים שממתינים לאישור או שנדחו, וההיעדרויות לפי סוג.
  - **לפי משמרות:** לכל משמרת מוצגים מספר השיבוצים, מספר הנציגים והימים, ממוצע נציגים ליום, פילוח לפי מיקום עבודה ולפי יום בשבוע, וטבלת היעדרויות לפי סוג.
  - לחיצה על כותרת עמודה ממיינת לפיה. לחיצה שנייה הופכת את הסדר, ולחיצה שלישית מחזירה לסדר המקורי.
  - ייצוא ל-Excel של התצוגה הנוכחית, עם שורת סיכום.
  - כל ימי הצוות נספרים לצוות שבו שובצו. נציג שעבר צוות במהלך התקופה יופיע בכל אחד מהצוותים, עם הימים שעבד בו.
  - הדוח זמין לכל מי שיש לו הרשאת צפייה בסידור, על הצוותים שלו.
- **ייצוא הסידור ל-Excel:** בסידור השבועי, בתפריט **"ייצוא ושיתוף"**. הוא מייצר גיליון לצוות, או גיליון לכל צוות. בקובץ מופיעים המשמרות, מיקומי העבודה, ההיעדרויות, החגים וסיכום הכיסוי היומי.

### מסך ראשי ותצוגה
- **מסך ראשי:** לכל צוות מוצג כרטיס עם ימי השבוע ומספר הנציגים בבוקר ובערב.
  - ימים בלי אף נציג בבוקר, או בערב כשיש משמרת ערב, מסומנים באדום.
  - מוצג גם כמה משבצות של נציגים פעילים לא שובצו, והסטטוס של השבוע הבא.
  - לחיצה על הכרטיס פותחת את הסידור של הצוות.
- **תפריט:** מחולק ל"עבודה שוטפת" ול"ניהול". מספר הבקשות הממתינות מהבהב כל עוד יש כאלה, ובאדום כשחלקן בתאריך שכבר הגיע.
- **לוגו החברה:** בהגדרות, בלשונית "כללי".
  - התמונה מוקטנת אוטומטית ונשמרת כ-PNG.
  - הלוגו מופיע בתפריט, במסך הכניסה, ב-PDF, בקובצי ה-Excel ובסידור ששותף עם הנציגים.
- **מצב כהה:** לפי הגדרת המכשיר, או בבחירה ידנית בתחתית התפריט (מערכת / בהיר / כהה).

### כלים לשיבוץ ולניהול
- **מינימום נציגים:** בעריכת צוות קובעים כמה נציגים צריך בבוקר ובערב.
  - במסך הראשי ובשורת "סה״כ ביום" בסידור, יום עם פחות נציגים מסומן באדום, ומוצג למשל "3/5".
  - 0 = התראה רק כשאין אף נציג.
- **ביטול פעולה:** אחרי פעולה גורפת (העתקה, מילוי, ניקוי, תבנית, שיבוץ מרוכז או היעדרות לטווח) מופיע "ביטול" בהודעה.
  - אפשר לבטל עד 15 דקות, רק את הפעולה האחרונה, ורק מי שביצע אותה.
  - משבצת ששונתה מאז לא משוחזרת.
  - יום בית שכבר אושר חוזר כבקשה חדשה.
- **הצע סידור:** כפתור בסידור השבועי. הוא מציע שיבוץ לכל המשבצות הריקות בשבוע, והמנהל רואה את ההצעה לפני שהיא נכנסת. הכללים:
  - כל נציג משובץ בימי העבודה, במשמרת ובמיקום הקבועים שלו.
  - כשיום לא מגיע למינימום של הצוות, עוברים לערב מי שעבדו הכי מעט ערבים ב-8 השבועות האחרונים ובשבוע הנוכחי. אותו דבר בכיוון ההפוך לבוקר.
  - יום בית משובץ רק כל עוד נשארה מכסה. אחרי זה הנציג משובץ במוקד, כך שלא נפתחות בקשות אישור.
  - "סבב שישי" (אופציונלי): בשישי ובערב חג משובצים רק כמה שהמינימום דורש, לפי מי שעבד הכי מעט ימי שישי.
  - לפני ההחלה מוצגים הכיסוי בכל יום, רשימת השיבוצים (עם הסיבה לכל שינוי מברירת המחדל), טבלת הוגנות ואזהרות על ימים שלא ניתן להשלים.
  - ההחלה ממלאת רק משבצות שעדיין ריקות, ואפשר לבטל אותה.
- **תבניות שבוע:** ב"כלי שיבוץ" ← "תבניות שבוע" שומרים שבוע בשם (למשל "שבוע רגיל") ומחילים אותו על כל שבוע.
  - ההחלה ממלאת רק ימים ריקים, ואפשר לבטל אותה.
  - עד 20 תבניות לצוות.
- **היסטוריה למשבצת:** בחלון השיבוץ, "היסטוריית שינויים" מציגה מי שינה את המשבצת ומתי, כולל החלטות על בקשות אישור.
- **חיפוש מהיר:** Ctrl+K (או אייקון החיפוש בטלפון) מחפש נציג, צוות או מסך. בחירת נציג פותחת את הסידור של הצוות שלו, עם השורה שלו מסומנת.
- **התקנה כאפליקציה:** אפשר להוסיף את המערכת למסך הבית בטלפון או במחשב, והיא נפתחת במסך מלא.
  - באנדרואיד/כרום: "הוספה למסך הבית" / "התקנה".
  - באייפון: שיתוף ← "הוסף למסך הבית".

### כל הצוותים ותפוסת עמדות

- **כל הצוותים ביחד:** בסידור עבודה, בבחירת הצוות, יש אפשרות "כל הצוותים". היא מציגה את השבוע של כל הצוותים בטבלה אחת, עם כותרת לכל צוות, וזה נוח במיוחד לאחמ״ש.
  - אפשר לחפש נציג, ולפתוח משבצת לצפייה או לעריכה לפי ההרשאות של הצוות שלה.
  - בתחתית הטבלה יש סיכום לכל המוקד: כמה נציגים בבוקר ובערב, וכמה מהם מכל מיקום (למשל "מוקד 7 · בית 2").
- **מספר עמדות:** בהגדרות ← מיקומי עבודה אפשר לקבוע למיקום (למשל המוקד) כמה עמדות יש בו. שורת "עמדות" מראה לכל יום את התפוסה בבוקר ובערב מול מספר העמדות.
  - **באדום, "חריגה":** שובצו למוקד יותר נציגים ממספר העמדות.
  - **בכתום, "פנויות":** נשארו עמדות פנויות, ובאותו זמן יש נציגים שעובדים מהבית.
- **בכל צוות בנפרד:** שורת הסיכום מציגה גם כמה מהצוות עובדים מכל מיקום, ושורת "עמדות · כל המוקד" מראה את התפוסה בכל המוקד. כך גם מנהל צוות רואה אם יש מקום לפני שהוא משבץ.

### נוכחות (מסך אחמ״ש)

מסך "נוכחות" מיועד לאחראי/ת המשמרת, ונוח גם בטלפון ובטאבלט.

- **מה מוצג:** הסידור של היום לכל הצוותים, מקובץ לפי צוות. המסך נפתח על המשמרת שפעילה עכשיו, ואפשר לעבור למשמרת אחרת, לצוות מסוים או ליום אחר.
- **טיוטה:** גם סידור שעוד לא פורסם מוצג, עם אזהרה שהוא עלול להשתנות.
- **סימון:** לכל נציג לוחצים על סטטוס: הגיע, איחר, לא הגיע, יצא מוקדם או חולה.
  - "איחר" ו"יצא מוקדם" מבקשים שעה. אם הוגדרו שעות למשמרת (הגדרות ← משמרות), המערכת מחשבת את דקות האיחור או היציאה המוקדמת.
  - לנציג שנוכח בוחרים מאיפה הוא עובד בפועל. מיקום ששונה מהסידור מסומן בצהוב.
  - אפשר להוסיף הערה, ולסמן בלחיצה אחת "הגיע" לכל מי שעוד לא סומן.
- **נציג שלא בסידור:** אפשר להוסיף נציג שהגיע למרות שלא שובץ, עם המשמרת והמיקום שלו.
- **סיכום:** למעלה מוצגים משובצים, הגיעו, איחורים, לא הגיעו ולא סומנו. לחיצה על ריבוע מסננת את הרשימה. במסך הראשי יש כרטיס עם הנוכחות במשמרת הנוכחית.
- **הסידור לא משתנה:** הנוכחות נשמרת בנפרד מהסידור, כדי להשוות בין התכנון לביצוע. כל סימון נרשם בלוג הפעולות, והמסך מתעדכן כל דקה.
- **סטטוסים:** נקבעים בהגדרות ← סטטוסי נוכחות. לכל סטטוס קובעים אם הנציג נחשב נוכח, ואם צריך להזין שעת הגעה או יציאה.
- **הרשאות:** "צפייה בנוכחות" ו"סימון נוכחות" (לכל הצוותים או לצוותים שלו). תפקיד **אחמ״ש** נוצר אוטומטית: צפייה בכל הצוותים, סימון נוכחות, אישור חריגים והעברות נציגים, בלי עריכת הסידור. מנהלת מוקד מקבלת גם את הנוכחות, ומנהל צוות יכול לצפות בנוכחות של הצוות שלו.

### מחיקת נציגים
בעריכת נציג יש כפתור **"מחיקה"**. אפשר למחוק רק נציג שאין לו היסטוריה, כלומר אין לו שיבוצים, בקשות אישור או העברות. למשל נציג שנוסף בטעות, או כפילות מייבוא קובץ. לנציג עם היסטוריה המערכת מציעה **השבתה** במקום: הנציג יוסר מהסידור ומהרשימות, והסידורים הקודמים והדוחות לא משתנים. מחיקה נרשמת ביומן הפעולות.

### ייבוא נציגים מקובץ
במסך **נציגים** ← **ייבוא מקובץ**. אפשר להוריד משם תבנית Excel, ובה רשימה נפתחת של הצוותים שבניהולך.
- הקובץ: Excel (xlsx) או CSV. CSV יכול להיות ב-UTF-8 או בקידוד של Excel בעברית (Windows-1255).
- העמודות: שם פרטי, שם משפחה, צוות ומספר עובד. מספר העובד לא חובה. במקום שני שדות השם אפשר עמודה אחת בשם "שם מלא" או "שם".
- הצוות מזוהה לפי השם, בלי תלות ברווחים או בגרש (דאצ׳יה = דאציה). לשורות בלי צוות אפשר לבחור צוות ברירת מחדל.
- לפני הייבוא מוצגת תצוגה מקדימה: אילו שורות יתווספו, אילו כבר קיימות (אותו שם באותו צוות, ולכן ידולגו) ואילו שגויות (צוות לא קיים או לא בהרשאתך, שם חסר, מספר עובד כפול). רק השורות התקינות מתווספות.
- כל נציג שנוסף נרשם ביומן הפעולות. אפשר עד 1000 שורות בקובץ.

### יצירת משתמשים (הזמנה במייל)

מנהל המערכת יוצר משתמש עם שם משתמש, שם מלא, מייל, תפקיד וצוותים, בלי סיסמה. Firebase שולח למשתמש מייל עם קישור לדף `/auth/action` במערכת. שם המשתמש בוחר סיסמה ונכנס אוטומטית. עד אז הוא מסומן ברשימה כ"ממתין להפעלה".

- הקישור תקף לשעה אחת. אפשר לשלוח אותו שוב מרשימת המשתמשים (אייקון המעטפה), והמשתמש יכול גם לבקש קישור חדש בעצמו מ"שכחתי סיסמה".
- אותו מנגנון משמש גם ל"שכחתי סיסמה" בדף ההתחברות, לפי שם משתמש או מייל. התשובה זהה בכל מקרה, כדי שאי אפשר יהיה לגלות אילו משתמשים קיימים.
- עדיין אפשר להגדיר סיסמה ידנית (אייקון המפתח), למשל למשתמש בלי מייל.
- מחיקת משתמש (אייקון הפח) מוחקת את החשבון לצמיתות ומסירה אותו מניהול הצוותים. ההיסטוריה נשמרת עם שמו, ושם המשתמש והמייל מתפנים לשימוש חוזר. אי אפשר למחוק את המשתמש שלך או את מנהל המערכת הפעיל האחרון. כדי רק לחסום כניסה, משביתים את המשתמש.

**הגדרת המייל נעשית אוטומטית בפריסה** (`npm run configure-auth`, נקרא מ-CI): הדומיין של האתר נוסף ל-Authorized domains, והקישור במייל מופנה ל-`https://<כתובת-האתר>/auth/action`, אם הפרויקט מאפשר זאת. בחלק מהפרויקטים Firebase נועל את הגדרות המייל (`EMAIL_TEMPLATE_UPDATE_NOT_ALLOWED`, כך גם בפרויקט ה-dev). אז הקישור פותח את הדף של Firebase לבחירת סיסמה, וכפתור "המשך" בו מחזיר לדף הכניסה (לפי `APP_URL` ב-`apphosting.<env>.yaml`). נוסח המייל הוא התבנית המובנית של Firebase בעברית, וזהה בהזמנה ובאיפוס סיסמה.
- ל-service account של הפריסה צריך להוסיף את התפקיד **Firebase Authentication Admin**.
- ב-production הכתובת נלקחת ממשתנה המאגר `APP_URL_PROD` (GitHub ← Settings ← Variables). כל עוד הוא לא מוגדר, השלב מדלג.

## אבטחת מידע

המערכת בנויה לפי הדרישות הטכניות של תקנות הגנת הפרטיות (אבטחת מידע), התשע"ז-2017. עמידה בתקנות דורשת גם צעדים ארגוניים: מסמך הגדרות מאגר, נוהל אבטחה, ממונה, הדרכה ומבדקים. את אלה צריך לבצע עם יועץ.

- **אימות דו-שלבי:** קוד מאפליקציית אימות בטלפון (TOTP: Google Authenticator, Microsoft Authenticator ודומות).
  - כל משתמש מפעיל אותו ב"החשבון שלי".
  - בהגדרות ← אבטחה אפשר לקבוע שהוא חובה. אז משתמש שעוד לא הגדיר אותו מופנה למסך ההגדרה ולא יכול להשתמש במערכת עד שיגדיר.
  - מנהל מערכת יכול לאפס את האימות של משתמש שהחליף טלפון, במסך המשתמשים.
  - המפתח הסודי נשמר באוסף נפרד (`userSecrets`) ולא נשלח לדפדפן. כל קוד תקף פעם אחת בלבד.
- **נעילת חשבון:** אחרי 5 ניסיונות כושלים (סיסמה או קוד) בתוך 15 דקות, החשבון ננעל ל-15 דקות. מנהל מערכת יכול לבטל את הנעילה במסך המשתמשים.
- **ניתוק אוטומטי:** אחרי זמן ללא פעילות, בברירת מחדל 30 דקות, והזמן נקבע בהגדרות ← אבטחה. דקה לפני הניתוק מוצגת הודעה. התחברות תקפה עד 12 שעות בכל מקרה.
- **תיעוד:** בלוג הפעולות נרשמים כניסה, ניסיון כושל, נעילה, ניתוק, יציאה, הפעלה ואיפוס של אימות דו-שלבי, ושינוי הגדרות אבטחה. ניסיונות עם שם משתמש שלא קיים נרשמים עם הגבלת קצב.
- **כותרות אבטחה:** אסור להציג את המערכת בתוך מסגרת של אתר אחר, והדפדפן מחויב ל-HTTPS (HSTS). נשלחות גם `nosniff` ו-Referrer-Policy.
- **קיים מההתחלה:** הרשאות לפי תפקיד וצוות, וחסימה מלאה של גישה ישירה למסד הנתונים (כל הגישה עוברת בשרת). בנוסף יש לוג שינויים, גיבוי יומי והתראות על תקלות.

## סביבות ופריסה

| Branch | סביבה | פרויקט Firebase |
|---|---|---|
| `dev` | פיתוח ובדיקות | `mishmarot-dev-cea4a` |
| `main` | production | `mishmarot-prod` |

**תהליך העבודה:** פיתוח ב-branch נפרד, ואז PR אל `dev`. אחרי merge, App Hosting פורס אוטומטית לסביבת dev ובודקים שם. אחרי אישור פותחים PR מ-`dev` אל `main`, ובסיום ה-merge הגרסה עולה ל-production.

GitHub Actions (`.github/workflows/ci.yml`) מריץ בכל PR את lint, typecheck, בדיקות יחידה, בדיקות אינטגרציה ו-build. ב-push ל-`dev` או ל-`main` הוא גם פורס את כללי האבטחה והאינדקסים של Firestore לפרויקט המתאים, ומוודא שקיים גיבוי יומי.

### גיבוי יומי
Firestore מגבה את מסד הנתונים פעם ביום, ושומר כל גיבוי 30 יום. את התזמון יוצר או מעדכן שלב בפריסה, `npm run configure-backups`. ל-service account של הפריסה צריך להוסיף את התפקיד **Cloud Datastore Backup Schedules Admin**.

- **רשימת הגיבויים:** Google Cloud Console ← Firestore ← Disaster recovery. או בשורת הפקודה:
  ```bash
  gcloud firestore backups list --project=<PROJECT_ID>
  ```
- **שחזור:** השחזור נעשה תמיד **למסד נתונים חדש**, כך שהנתונים הנוכחיים לא נדרסים:
  ```bash
  gcloud firestore databases restore --project=<PROJECT_ID> \
    --source-backup=projects/<PROJECT_ID>/locations/<LOCATION>/backups/<BACKUP_ID> \
    --destination-database=restored-YYYYMMDD
  ```
  אחרי השחזור בודקים את הנתונים במסד החדש, ומעבירים ממנו את מה שצריך. אפשר גם לפנות למפתח.
- **עלות:** לפי נפח הגיבוי. בגודל של מוקד מדובר באגורות בחודש.

### התראות על תקלות (Error Reporting)
כל שגיאה לא צפויה נרשמת ביומן של App Hosting, במבנה ש-**Google Cloud Error Reporting** מזהה:
- שגיאות בשרת: בדף, בפעולה או בהורדת קובץ (`src/instrumentation.ts`, ו-`runAction` ב-`src/lib/action.ts`).
- שגיאות בדפדפן: נשלחות ל-`/client-error` (`src/instrumentation-client.ts` ומסכי השגיאה).

Error Reporting מקבץ שגיאות זהות ומראה מתי התחילו ובאיזו גרסה. המשתמש רואה מסך "משהו השתבש" עם "קוד תקלה", ואפשר לחפש את הקוד ביומן. שגיאות צפויות, כמו אין הרשאה, לא נמצא או הפניה, לא נרשמות. גם פרטים אישיים לא נרשמים, רק מזהה המשתמש.

הגנה מהצפה: הכתובת `/client-error` פתוחה, כדי שגם תקלות במסך הכניסה יירשמו. לכן:
- דיווחים של אורח לא מחובר מתקבצים כולם לתקלה אחת קבועה. לא ניתן ליצור דרכם "סוגי תקלות" חדשים, ולכן גם לא מיילים חדשים.
- משתמש מחובר יכול לדווח עד 10 תקלות בשעה, ודיווחיו נושאים את מזהה המשתמש. השרת כולו מקבל עד 60 דיווחים בדקה.
- אותה תקלה מאותו שולח נרשמת פעם אחת בעשר דקות.
- Error Reporting שולח מייל רק על סוג תקלה חדש, לא על כל הופעה.

הפעלת התראות במייל (פעם אחת לכל פרויקט, dev ו-prod):
1. ב-[Google Cloud Console](https://console.cloud.google.com/errors) בוחרים את הפרויקט ופותחים **Error Reporting**. אם מופיעה בקשה להפעיל את ה-API, מאשרים.
2. לוחצים **Configure notifications**.
3. תחת **Notification channels** מוסיפים ערוץ **Email** עם הכתובת שצריכה לקבל התראות, ושומרים.
4. מסמנים את הערוץ ושומרים. מעכשיו נשלח מייל על כל שגיאה **חדשה**, כלומר על הופעה ראשונה של שגיאה מסוג שלא נראה קודם, ועל שגיאה ישנה שחזרה.

## מדריך הקמה ב-Firebase (פעם אחת לכל סביבה)

חוזרים על השלבים פעמיים: פעם ל-`mishmarot-dev` ופעם ל-`mishmarot-prod`.

1. **יצירת פרויקט:** ב-[Firebase Console](https://console.firebase.google.com) ← Add project. אם השם `mishmarot-dev` תפוס, Firebase יציע מזהה אחר. במקרה כזה עדכנו את המזהה בקובץ `.firebaserc`.
2. **תוכנית Blaze:** ⚙️ ← Usage and billing ← Blaze. App Hosting דורש חיבור כרטיס אשראי. בהיקף של מוקד העלות צפויה להיות אפסית או קרובה לאפס. מומלץ להגדיר תקציב והתראה ב-Google Cloud Billing.
3. **Firestore:** Build ← Firestore Database ← Create database. בוחרים מיקום (למשל `europe-west1` או `me-west1` תל אביב) ומצב **Production**.
4. **Authentication:** Build ← Authentication ← Get started ← Sign-in method ← מפעילים **Email/Password**. המערכת משתמשת בו מאחורי הקלעים עבור שם משתמש וסיסמה.
5. **Web API Key:** ⚙️ Project settings ← General ← מעתיקים את **Web API Key** ומדביקים בקובץ `apphosting.dev.yaml` (או `apphosting.prod.yaml`) במקום `REPLACE_WITH_...`. זה מזהה ציבורי, לא סוד.
6. **App Hosting:** Build ← App Hosting ← Create backend:
   - מחברים את GitHub ובוחרים את הריפו `elorsh95/mishmarot`.
   - Root directory: `/`. Live branch: `dev` בפרויקט ה-dev, או `main` בפרויקט ה-prod.
   - מפעילים **Automatic rollouts**.
   - אחרי היצירה: Backend ← Settings ← Environment ← **Environment name**: `dev` או `prod`, בהתאמה.
7. **Service account ל-GitHub Actions:** ⚙️ Project settings ← Service accounts ← Generate new private key. ב-GitHub: Settings ← Secrets and variables ← Actions ← New repository secret בשם `FIREBASE_SERVICE_ACCOUNT_DEV` (או `FIREBASE_SERVICE_ACCOUNT_PROD`), ומדביקים את כל תוכן קובץ ה-JSON. **אל תשמרו את הקובץ בריפו.**
8. **הקמת נתוני בסיס ומשתמש מנהל ראשון:** מתבצעת אוטומטית ב-GitHub Actions בכל push ל-`dev`/`main`, יחד עם פריסת הכללים והאינדקסים. כדי שייווצר משתמש מנהל, מוסיפים ב-GitHub את ה-secrets `BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_NAME` ו-`BOOTSTRAP_ADMIN_PASSWORD`. אם המשתמש כבר קיים, השלב מדלג עליו. אפשר גם להריץ ידנית מהמחשב:
   ```bash
   GOOGLE_APPLICATION_CREDENTIALS=./service-account.json FIREBASE_PROJECT_ID=mishmarot-dev-cea4a \
     npm run bootstrap -- --username admin --name "השם שלך" --password "סיסמה-חזקה1"
   ```
9. **Firestore indexes:** נפרסים אוטומטית ב-push הראשון ל-`dev`/`main` (שלב 7). אפשר גם ידנית: `npx firebase deploy --only firestore --project dev`.

- **מסך חדש:** תיקייה ב-`src/app/(app)/<route>` עם `page.tsx` ו-`actions.ts`, ופריט ב-`src/components/layout/nav-items.ts`.
- **הרשאה חדשה:** מוסיפים מפתח ב-`src/modules/permissions/catalog.ts`, בודקים אותו ב-service, ומעניקים אותה לתפקידים במסך "תפקידים והרשאות".

- **התראות:** מאזינים לאירועים ב-`src/lib/events.ts`.
